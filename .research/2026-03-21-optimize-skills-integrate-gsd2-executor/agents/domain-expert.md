# Research Findings: Domain Expert

## Executive Summary

gw-skills can be meaningfully optimized through three vectors: (1) migrating from `.claude/commands/` to `.claude/skills/` directory structure to unlock subagent execution, lifecycle hooks, and dynamic context injection; (2) applying empirically-validated description optimization patterns that improve skill activation rates from ~20% to 84%; and (3) integrating GSD-2 as an autonomous plan executor by leveraging its disk-based state machine, fresh-context-per-task model, and headless mode to consume plans generated by gw-skills like `research`, `compete`, and `review-app`.

## Key Findings

### Finding 1: gw-skills Use Legacy Command Format, Missing Modern Skill Features

All gw-skills currently live under `.claude/commands/gw/` rather than `.claude/skills/gw/`. According to official Claude Code documentation, skills in the commands directory "keep working" but miss features that the skills directory unlocks: `context: fork` for subagent isolation, `agent` field for execution environment selection, lifecycle `hooks` in frontmatter, `model` override per skill, and `effort` level control. The current gw-skills already behave like task-oriented skills (multi-step orchestration with agent spawning), making them prime candidates for these advanced features. Migration path is straightforward since the YAML frontmatter format is identical.

- **Source:** https://code.claude.com/docs/en/skills
- **Confidence:** High

### Finding 2: Skill Description Optimization Has Outsized Impact on Activation

Research across 200+ prompts shows that skill activation rates vary dramatically based on description quality: baseline ~20%, optimized descriptions 50%, and with evaluation hooks 84%. Three rules are empirically validated: (1) use third-person language only (descriptions inject into system prompts), (2) two-part structure stating capabilities then trigger conditions using "USE WHEN" patterns, (3) include exact workflow keywords. Current gw-skill descriptions are functional but don't follow the "USE WHEN" pattern. For example, `review-app`'s description is "Full-stack application review -- security, architecture, UX, testing, cloud cost analysis with AI specialists" but lacks trigger conditions. An optimized version would append: "Use when auditing an application, performing security review, preparing for production deployment, or when asked to analyze app quality."

- **Source:** https://gist.github.com/mellanon/50816550ecb5f3b239aa77eef7b8ed8d
- **Confidence:** High

### Finding 3: GSD-2 Is a Standalone CLI With Disk-Based State Machine Ideal for Plan Execution

GSD-2 is no longer a Claude Code prompt framework (v1) but a standalone CLI built on the Pi SDK. Its core architecture decomposes work into Milestone > Slice > Task, where each task fits in a single context window. A disk-based state machine reads `.gsd/STATE.md` to determine the next work unit and dispatches fresh 200k-token context windows per task. This addresses "context rot" -- the quality degradation gw-skills experience during long orchestration runs. Key execution guarantees include: git worktree isolation per milestone, pre-inlined file context, verification command enforcement with auto-fix retries, sequential commits within milestone branches, and squash-merge to main on completion.

- **Source:** https://github.com/gsd-build/gsd-2
- **Confidence:** High

### Finding 4: GSD-2 Headless Mode Enables Programmatic Integration

GSD-2's headless mode (`gsd headless [cmd]`) is designed for CI pipelines, cron jobs, and scripted automation. It auto-responds to interactive prompts, returns structured exit codes (0=complete, 1=error/timeout, 2=blocked), and supports file-based IPC via `.gsd/parallel/` for multi-worker orchestration. The `gsd headless query` subcommand provides instant (~50ms) machine-readable JSON state snapshots without spawning an LLM session. This is the natural integration point for gw-skills: a skill like `research` or `compete` generates a plan, writes it to `.gsd/` format, and invokes `gsd headless auto` to execute it autonomously.

- **Source:** https://github.com/gsd-build/gsd-2
- **Confidence:** High

### Finding 5: gw-skills Already Have a GSD Detection Mechanism

The existing `preamble.md` shared module already checks for GSD project state (`.planning/config.json`) and inherits model profiles. This is a v1 GSD integration. Upgrading to GSD-2 integration would mean: (1) detecting `.gsd/STATE.md` instead of `.planning/config.json`, (2) reading GSD-2 preferences for model selection (quality/balanced/budget profiles), and (3) offering to hand off generated plans to GSD-2 execution when detected. The migration path from v1 to v2 state is supported by GSD-2's built-in `/gsd migrate` command.

- **Source:** Codebase analysis of `/Users/wohlgemuth/skills/.claude/commands/gw/_shared/preamble.md`
- **Confidence:** High

### Finding 6: Fresh Context Per Task Is the Key to Quality at Scale

The METR study found experienced developers using AI tools took 19% longer on tasks, contradicting expectations of a 24% speedup. A significant contributing factor was context-switching overhead and accumulated context degradation. GSD-2's architecture directly addresses this: every task, research phase, and planning step receives a clean context window. For gw-skills, the longest-running skills (`review-app`, `research`, `compete`) spawn multiple agents sequentially within a single context window. If these skills emitted GSD-2-compatible task plans instead, each phase would execute in isolation with full 200k-token capacity.

- **Source:** https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/
- **Confidence:** Medium

### Finding 7: Dynamic Context Injection Can Replace Boilerplate Preamble Resolution

Claude Code now supports `!`command`` syntax in skill files to run shell commands before content reaches the LLM. The current gw-skills preamble requires the LLM to execute bash to resolve `GW_REPO`, read the preamble file, and follow its instructions -- consuming tokens and tool calls. With dynamic context injection, the preamble could be pre-resolved: `!`bash "$GW_REPO/check-update.sh" 2>/dev/null`` would inject the update check result directly, and `!`cat "$GW_REPO/.claude/commands/gw/_shared/preamble.md"`` would inline the preamble before Claude sees it. This saves 2-3 tool calls per skill invocation.

- **Source:** https://code.claude.com/docs/en/skills (dynamic context injection section)
- **Confidence:** High

### Finding 8: Skill File Size Should Stay Under 500 Lines With Progressive Disclosure

Official Anthropic guidance and community best practices converge on keeping SKILL.md under 500 lines. The current gw-skills are significantly larger -- `worktree.md` is 562 lines, and `review-app.md` and `research.md` exceed 500 lines each based on token counts. The recommended architecture separates process (in SKILL.md) from reference material (in supporting files). For gw-skills, the shared modules (`_shared/preamble.md`, `_shared/branch-first.md`, `_shared/team-assembly.md`) already follow this pattern, but the main skill files should be further decomposed.

- **Source:** https://gist.github.com/mellanon/50816550ecb5f3b239aa77eef7b8ed8d; https://code.claude.com/docs/en/skills
- **Confidence:** High

### Finding 9: The Industry Is Converging on Multi-Agent Orchestration With Standardized Protocols

Gartner reported a 1,445% surge in multi-agent system inquiries from Q1 2024 to Q2 2025. MCP (Model Context Protocol) has become the de facto standard with 1,000+ community servers, and OpenAI plans to sunset their Assistants API in mid-2026 in favor of MCP compatibility. GitHub's Agent HQ (February 2026) allows running Claude, Codex, and Copilot simultaneously on the same task. The gw-skills `worktree execute` subcommand already implements multi-agent orchestration with dependency-graph-based wave execution -- this aligns with industry direction and could be enhanced by delegating individual task execution to GSD-2.

- **Source:** https://aimultiple.com/agentic-orchestration; https://dev.to/blackgirlbytes/my-predictions-for-mcp-and-ai-assisted-coding-in-2026-16bm
- **Confidence:** Medium

### Finding 10: GSD-2 Model Profiles Enable Cost-Aware Execution

GSD-2 supports three model profiles: Quality (Opus for all phases), Balanced (Opus planning, Sonnet execution/verification), and Budget (Sonnet planning, Haiku verification). The token overhead is reported at 4:1 ratio -- for every token of useful output, four tokens are consumed in orchestration. This means cost management is essential. gw-skills could expose a `--gsd-profile` flag that maps to GSD-2's model profiles, letting users choose between quality and cost when handing off to GSD-2 execution.

- **Source:** https://dev.to/alikazmidev/the-complete-beginners-guide-to-gsd-get-shit-done-framework-for-claude-code-24h0
- **Confidence:** Medium

## Areas of Consensus

1. **Context window management is the primary bottleneck for AI agent quality.** Both GSD-2's architecture and the METR study point to context degradation as the dominant failure mode. Fresh context per task is the most impactful optimization. gw-skills, academic research, and GSD-2 all converge on this.

2. **Skill descriptions are the activation bottleneck.** Official Anthropic documentation, community research, and practical usage all agree that vague descriptions cause skills to be ignored regardless of instruction quality. The "USE WHEN" pattern is universally recommended.

3. **Multi-agent orchestration with isolation is the correct architecture.** GSD-2's worktree isolation, Claude Code's `context: fork`, and gw-skills' `worktree execute` all implement the same principle: give each agent a clean, bounded workspace. Industry-wide adoption confirms this pattern.

4. **Plan-then-execute separation improves outcomes.** GSD-2, gw-skills, and multiple industry frameworks all separate planning from execution. The debate is only about where the boundary sits and who does each phase.

## Areas of Disagreement

1. **Standalone CLI vs. skill-native execution.** GSD-2 moved away from Claude Code slash commands to a standalone CLI for programmatic control. gw-skills remain fully within the Claude Code skill ecosystem. Integration means bridging these two models -- which is the orchestrator? A gw-skill that invokes GSD-2, or GSD-2 that consumes gw-skill output? Both are viable; the choice depends on whether the user wants to stay in Claude Code's conversational model or delegate to a fully autonomous process.

2. **Token overhead vs. quality trade-off.** GSD-2's 4:1 token ratio is significant. For simple tasks, the overhead doesn't justify the quality gain. Community feedback suggests GSD-2 shines for multi-hour autonomous work but is overkill for tasks under 30 minutes. gw-skills serve both quick and deep workflows, so a conditional hand-off (only invoke GSD-2 when plan complexity exceeds a threshold) may be optimal.

3. **AI developer productivity impact.** The METR study found a 19% slowdown for experienced developers using AI tools, while industry surveys report 26% productivity gains and 69% of developers reporting increased productivity. The discrepancy likely reflects different task types, experience levels, and tool maturity -- but it means optimization claims should be treated with caution.

## Practical Implications

### For gw-skills Optimization

1. **Migrate to `.claude/skills/` directory structure.** This is the highest-impact, lowest-effort optimization. It unlocks `context: fork`, lifecycle hooks, model overrides, effort levels, and subagent type selection without changing any skill logic.

2. **Rewrite all skill descriptions using the "USE WHEN" pattern.** Add explicit trigger conditions to every skill description. This alone could double activation rates for model-invoked scenarios.

3. **Implement dynamic context injection for the preamble.** Replace the current "read and follow preamble" pattern with `!`command`` preprocessing to save 2-3 tool calls per invocation.

4. **Decompose large skills using progressive disclosure.** Move reference sections, error handling blocks, and detailed specifications into supporting files. Keep SKILL.md as an orchestration playbook under 500 lines.

5. **Add `allowed-tools` restrictions.** Skills like `weekly-review` and `log-patrol` that only need read access should restrict tools to prevent unintended modifications.

### For GSD-2 Integration

1. **Add a `--gsd` flag to plan-producing skills.** When present, skills like `research`, `compete`, `review-app`, and `saas-idea` would emit their implementation plans in GSD-2 `.gsd/` format (ROADMAP.md, milestone/slice/task structure) instead of or in addition to their current output format.

2. **Update preamble.md to detect GSD-2 state.** Check for `.gsd/STATE.md` in addition to the current `.planning/config.json` detection. When GSD-2 is detected, inherit its model profile and offer plan hand-off.

3. **Create a `gw:gsd` bridge skill.** A dedicated skill that converts any existing gw-skills plan output into GSD-2 format and optionally triggers execution via `gsd headless auto`. This decouples the conversion from individual skills.

4. **Use GSD-2's headless query for status monitoring.** A `gw:gsd-status` skill or integration into `gw:worktree status` that calls `gsd headless query` for instant JSON state snapshots of running GSD-2 executions.

## Knowledge Gaps

1. **GSD-2 plan format specification.** While GSD-2's `.gsd/` directory structure is documented at a high level (STATE.md, ROADMAP.md, milestones/), the exact schema for task plans (XML structure with verification criteria mentioned in community docs) is not fully documented in public sources. Integration would require inspecting actual `.gsd/` output or consulting GSD-2's source code.

2. **Claude Code Skills 2.0 lifecycle hooks API.** The SubagentStart hook and PostToolUse/PreToolUse hooks are documented, but real-world performance characteristics (latency overhead, failure modes) are not well-covered in available sources.

3. **Interaction between `context: fork` and gw-skills' agent spawning.** gw-skills already spawn agents internally (e.g., `worktree execute` dispatches agents per feature). Whether wrapping the entire skill in `context: fork` conflicts with internal agent spawning, or composes cleanly, is not documented.

4. **GSD-2 API stability.** GSD-2 is relatively new. Whether its `.gsd/` format, headless CLI interface, and exit codes constitute a stable API for external integration is unclear. Tight coupling to undocumented internals could break with updates.

5. **Token budget impact of skill descriptions at scale.** With 10+ gw-skills, each description consumes part of the 2% context window budget for skill descriptions. Whether the current descriptions collectively approach this limit, and how optimized descriptions affect the budget, has not been measured.
