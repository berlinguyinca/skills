# Research Findings: Backend Engineer

## Executive Summary

GW-skills can be optimized through progressive disclosure (splitting large SKILL.md files), better description tuning for activation reliability, and adopting the `context: fork` subagent pattern for isolation. GSD-2 is a standalone CLI plan executor with a milestone/slice/task hierarchy, file-based state machine, crash recovery, and headless mode — making it a natural fit for executing multi-step plans generated by gw-skills like `research` and `review-app`, either via its headless CLI or through Claude Code's `-p` flag bridging the two systems.

## Key Findings

### Finding 1: GSD-2 Architecture Is a File-Based State Machine with Crash Recovery

GSD-2 decomposes work into a strict hierarchy: Milestones (shippable versions, 4-10 slices), Slices (demoable capabilities, 1-7 tasks), and Tasks (context-window-sized units, ~200k tokens each). Each task gets a fresh agent session to prevent context degradation. State is persisted to `.gsd/` directory files including `STATE.md`, `PLAN.md`, `CONTEXT.md`, and `completed-units.json`. Crash recovery uses lock files, PID liveness detection, and exponential backoff (3 retries default). Transient provider errors (rate limits, 5xx) auto-resume; permanent errors (auth, billing) pause for manual review.

- **Source:** https://github.com/gsd-build/GSD-2
- **Confidence:** High

### Finding 2: GSD-2 Headless Mode Enables CI/Pipeline Integration

GSD-2's headless mode (`gsd headless [cmd]`) removes the TUI and is designed for cron jobs, CI pipelines, and scripted automation. It auto-responds to interactive prompts and exits with structured codes: 0=complete, 1=error/timeout, 2=blocked. This is the primary integration surface for gw-skills. A gw-skill could generate a plan, write it to `.gsd/PLAN.md`, and invoke `gsd headless` to execute it autonomously.

- **Source:** https://github.com/gsd-build/GSD-2
- **Confidence:** High

### Finding 3: Claude Code Skills Support Progressive Disclosure and Subagent Forking

Official Claude Code documentation recommends keeping SKILL.md under 500 lines and splitting reference material into separate files. The `context: fork` frontmatter runs a skill in an isolated subagent with a fresh context window. The `agent` field specifies which subagent type to use (`Explore`, `Plan`, `general-purpose`, or custom agents from `.claude/agents/`). Skill descriptions consume a budget of 2% of the context window (fallback 16,000 characters); excessive skills may be excluded.

- **Source:** https://code.claude.com/docs/en/skills
- **Confidence:** High

### Finding 4: Skill Description Quality Directly Impacts Activation Reliability

According to the Claude Code skills gist, properly optimized descriptions can improve skill activation from 20% to 50%, and adding concrete examples further improves it from 72% to 90%. Descriptions should be written in third person, include both what the skill does and when to use it, and contain specific trigger keywords. The current gw-skills descriptions are functional but could benefit from more specific trigger phrases.

- **Source:** https://gist.github.com/mellanon/50816550ecb5f3b239aa77eef7b8ed8d
- **Confidence:** Medium (single-source benchmark numbers, but consistent with Anthropic's official guidance)

### Finding 5: GSD-2's Verify-Fix Loop Maps Directly to gw-skills Quality Gates

GSD-2 runs configured shell commands (lint, test) automatically after task execution. Failures trigger auto-fix retries before advancing. A milestone validation gate compares roadmap success criteria against actual outcomes. This pattern aligns with gw-skills' existing approval gates (e.g., after Step 2, 3, and 5 in research.md) but could be made more rigorous by adopting GSD-2's machine-verifiable validation approach instead of human-only approval.

- **Source:** https://github.com/gsd-build/GSD-2
- **Confidence:** High

### Finding 6: The "God Agent" Anti-Pattern Applies to Large gw-Skills

Research on AI agent reliability shows that agent routing accuracy drops from 95% with 5 tools to 70% with 25 tools. The recommended minimum viable production agent pattern is: specialist scope (1 agent, 1 job, 3-5 tools max), error recovery with circuit breaker on every external call, and hard budget limits on steps/cost/runtime. Skills like `review-app` with 12+ skip flags and many dimensions may benefit from decomposition into smaller specialist agents.

- **Source:** https://dev.to/nebulagg/why-90-of-ai-agent-projects-fail-and-the-patterns-that-fix-it-1dma
- **Confidence:** Medium (industry patterns, not gw-skills-specific benchmarks)

### Finding 7: Claude Code Headless Mode Provides Programmatic Bridge for GSD-2 Integration

Claude Code's `-p` flag enables non-interactive execution with structured JSON output, session continuation (`--continue`/`--resume`), tool auto-approval (`--allowedTools`), and custom system prompts (`--append-system-prompt`). Stream-JSON output includes retry events with error categorization. This makes it possible to build a bridge where GSD-2 dispatches tasks to Claude Code headless sessions, or where a gw-skill generates a GSD-2 plan and hands off execution.

- **Source:** https://code.claude.com/docs/en/headless
- **Confidence:** High

### Finding 8: GSD's File-Based State Is Already Partially Compatible with gw-skills

The gw-skills preamble (`_shared/preamble.md`) already includes GSD project detection — checking for `.planning/config.json` and inheriting model profiles. GSD v1 used a `.planning/` directory structure with `PROJECT.md`, `REQUIREMENTS.md`, `ROADMAP.md`, and `STATE.md`. GSD-2 uses `.gsd/` instead. The existing detection logic would need updating to recognize GSD-2's state directory.

- **Source:** `/Users/wohlgemuth/skills/.claude/commands/gw/_shared/preamble.md` (local file)
- **Confidence:** High

### Finding 9: Budget Enforcement Is Critical for Autonomous Execution

Multiple sources converge on four guardrails for autonomous agents: step count limits (prevent loops), cost caps (prevent budget overruns), runtime limits (prevent hung agents), and consecutive tool detection (catch repeated calls). GSD-2 implements budget ceilings with preemptive pause and sliding-window stuck detection. Any gw-skills integration should inherit or respect these budget controls rather than implementing its own.

- **Source:** https://dev.to/nebulagg/why-90-of-ai-agent-projects-fail-and-the-patterns-that-fix-it-1dma, https://github.com/gsd-build/GSD-2
- **Confidence:** High

### Finding 10: GSD-2 Supports Parallel Orchestration via File-Based IPC

GSD-2 uses `.gsd/parallel/` for coordinating multiple workers across milestones with fleet-level budgeting. This maps well to gw-skills' existing branch-first concurrent execution pattern (`_shared/branch-first.md`) and the `merge-prs` skill. A potential integration could have GSD-2 orchestrate parallel gw-skill executions across worktrees.

- **Source:** https://github.com/gsd-build/GSD-2
- **Confidence:** Medium (parallel orchestration documented but integration path is speculative)

## Areas of Consensus

1. **Fresh context per task is essential.** GSD-2, Claude Code's `context: fork`, and the agent reliability literature all agree that accumulated context degrades output quality. The gw-skills that spawn subagents already follow this pattern; skills that run inline should consider forking.

2. **File-based state persistence is the right approach for agent orchestration.** Both GSD-2 (`.gsd/` files) and gw-skills (`.research/`, `.analysis/`, `.planning/`) use Markdown files with structured content. This enables human readability, version control, and crash recovery.

3. **Validation loops improve reliability.** GSD-2's auto-fix retries, Claude Code's skill best practices (plan-validate-execute), and the agent reliability research all recommend machine-verifiable intermediate outputs with retry on failure.

4. **Budget enforcement is non-negotiable for autonomous execution.** Every source covering autonomous agents emphasizes hard limits on cost, steps, and runtime.

## Areas of Disagreement

1. **Human-in-the-loop vs. fully autonomous.** GSD-2's auto mode runs fully autonomously with headless support. gw-skills currently have approval gates at multiple steps. The right balance depends on the use case — research may benefit from human checkpoints, but execution of well-defined plans could go fully autonomous.

2. **Orchestration layer placement.** GSD-2 positions itself as the orchestrator dispatching tasks to Claude Code sessions. An alternative approach is having Claude Code (via gw-skills) be the orchestrator that generates GSD-2-compatible plans. The integration direction significantly affects architecture.

3. **State directory structure.** GSD v1 used `.planning/`, GSD-2 uses `.gsd/`. gw-skills currently detect `.planning/` for GSD project compatibility. Migrating detection to support both introduces complexity.

## Practical Implications

1. **Immediate skill optimization (low effort):**
   - Audit all gw-skill descriptions for third-person voice, specific trigger keywords, and when-to-use guidance.
   - Ensure all SKILL.md files are under 500 lines; split large reference sections into supporting files.
   - Override the `SLASH_COMMAND_TOOL_CHAR_BUDGET` env var if skill descriptions are being truncated.

2. **Subagent isolation (medium effort):**
   - Add `context: fork` to skills that perform isolated analysis (e.g., individual research agents in `research.md` already spawn subagents, but the orchestrator itself could benefit from forking certain phases).
   - Use `allowed-tools` to restrict tool access per skill, improving reliability by reducing routing errors.

3. **GSD-2 integration — plan generation path (medium effort):**
   - Add a `--gsd2` flag to skills like `research` and `review-app` that outputs a GSD-2-compatible plan file (milestone/slice/task YAML) to `.gsd/PLAN.md`.
   - User then runs `gsd headless` to execute the plan autonomously.
   - This is the safest integration path: gw-skills generate, GSD-2 executes, no tight coupling.

4. **GSD-2 integration — direct invocation path (higher effort):**
   - Build a bridge skill (e.g., `gw:execute`) that writes a plan to `.gsd/`, invokes `gsd headless` via Bash, monitors exit codes, and reports results.
   - Requires GSD-2 to be installed and configured in the user's environment.
   - Must handle GSD-2's exit codes (0/1/2) and surface blocked states to the user.

5. **Update preamble for GSD-2 detection:**
   - Extend `_shared/preamble.md` to detect `.gsd/STATE.md` alongside `.planning/config.json`.
   - Inherit GSD-2's model preferences and budget settings when running inside a GSD-2 project.

6. **Add budget guardrails to autonomous skill paths:**
   - Any skill running in autonomous mode (no approval gates) should enforce step count, cost, and runtime limits.
   - GSD-2's budget ceiling feature can be inherited if running within a GSD-2 project.

## Knowledge Gaps

1. **GSD-2 plan file format specification.** The exact schema for `.gsd/PLAN.md` (milestone/slice/task structure, checkbox format, metadata requirements) is not fully documented in public sources. Generating compatible plans requires either reverse-engineering from examples or upstream documentation.

2. **GSD-2 API stability guarantees.** GSD-2 is at v2.41.0 with active development. The file-based state format may change between versions. No semantic versioning contract for the state file format was found.

3. **Performance benchmarks for skill activation.** The 20%/50%/90% activation numbers come from a single community source. No official Anthropic benchmarks for skill discovery accuracy were found.

4. **GSD-2 + Claude Code headless interop.** No documented examples of GSD-2 dispatching work to Claude Code via `-p` flag were found. The integration path exists architecturally but hasn't been validated in practice.

5. **Token budget impact of many gw-skills.** With 10+ skills registered, the description budget (2% of context window) may become a constraint. No measurement of current gw-skills description footprint was performed.

6. **GSD-2 licensing and dependency requirements.** GSD-2 is built on the Pi SDK with TypeScript; its exact runtime requirements and license terms were not fully enumerated in this research.
